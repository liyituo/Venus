# Venus 项目介绍 PPT 大纲

> 建议用途：技术项目展示、课程答辩或小团队内部介绍。建议 13 页，讲述约 15～18 分钟；如需压缩到 10 分钟，可合并第 5～6 页、第 10～11 页。本文是逐页内容大纲，不是已经完成的幻灯片。

## 汇报主线

**一句话概括：**Venus 是一个本地可控的 Agent 调度台。用户用自然语言提出任务，系统调用电脑和开发工具执行，保存过程与结果，并通过确认、隔离和审阅控制风险。

整场汇报围绕四个问题展开：

1. Agent 如何把一句话变成可检查的执行过程？
2. 长任务与跨会话工作如何持续推进？
3. 系统如何记住有用信息，同时控制上下文开销？
4. 当任务进入团队环境，如何划清身份、权限与代码变更边界？

## 逐页大纲

### 第 1 页｜封面：Venus，个人 Agent 调度台

**本页要传达：**项目名称与核心定位，让听众知道接下来讲的是一个能实际执行任务的本地工作台。

**建议上屏文字：**

- 标题：Venus，个人 Agent 调度台
- 副标题：从自然语言派活，到可追踪的任务交付
- 页脚：汇报人、日期、项目版本（按汇报当天填写）

**画面建议：**使用 VenusChat 的真实界面截图作为主体，保留输入框、对话和任务区域。截图前遮盖 API Key、个人路径、会话内容等敏感信息。

**讲述提示：**开场只用一句话解释项目：用户描述目标，Venus 负责调用工具、跟踪执行，并把关键操作交还给用户确认。

---

### 第 2 页｜项目定位：让任务在一个工作台内完成

**本页要传达：**Venus 的价值来自完整工作流，而不是单次问答。

**建议上屏内容：**

- **输入：**用户描述目标，例如“检查这个仓库的测试失败，修复问题并汇报改动”。
- **执行：**Agent 检索代码、运行命令、编辑文件；需要确认的操作暂停等待用户决定。
- **交付：**产出文件改动、运行结果与任务记录，后续会话仍可查到相关状态。
- **定位：**以本地工作区和用户授权为边界，支持个人使用，也支持受控的团队任务。

**画面建议：**用一条横向流程表示“目标描述 → 工具执行 → 确认与检查 → 结果交付”。每个环节放一个真实界面或终端截图的局部；没有截图时只保留流程文字。

**讲述提示：**这里介绍的是工作方式。上面的仓库任务是演示脚本，不应说成已经完成的真实项目案例。

---

### 第 3 页｜总体架构：多入口共用一个执行中枢

**本页要传达：**前端可以更换，任务、权限、记忆和工具调用由同一个后端管理。

**建议上屏内容：**

1. **入口层：**VenusChat 桌面端、CLI、网页和 Telegram 接入后端。
2. **中枢层：**`llm_server` 管理会话、Agent 工具循环、异步任务、确认流程、记忆、定时调度与 MCP。
3. **执行层：**屏幕 daemon、文件与代码工具、命令执行、浏览器和外部 MCP 工具。
4. **本地数据：**`.venus/` 保存会话、任务、记忆、备份及日志；配置和密钥文件不进入仓库。

**画面建议：**绘制四层架构图，主线从“入口”流向“中枢”，再分到“执行工具”和“本地数据”。在图旁标明个人屏幕 daemon 与团队 Hub 的边界，避免让听众误以为远程团队任务能直接操控成员电脑。

**讲述提示：**点出架构取舍：前端负责交互，后端掌握任务状态和安全判断；团队 Hub 运行在隔离模式，个人屏幕和键鼠保持本机私有。

### 第 4 页｜亮点一：对话可以调用真实工具

**本页要传达：**Venus 已具备覆盖日常开发与电脑操作的工具链，并能通过扩展机制增加能力。

**建议上屏内容：**

| 工具类别 | 代表操作 | 适合展示的结果 |
| --- | --- | --- |
| 文件与代码 | 浏览、检索、读写、精确替换、符号查看 | 文件差异、检索结果 |
| 开发流程 | Git 状态、差异、日志、提交；运行测试和命令 | 测试输出、提交预览 |
| 电脑交互 | 截图、鼠标键盘、浏览器操作 | 操作前后的界面 |
| 扩展能力 | Skill、专业子 Agent、MCP 工具 | 按任务加载的能力与返回结果 |

**画面建议：**左侧放一句用户请求，右侧放真实工具卡片或日志片段，突出“模型决定调用什么工具”这一过程。不要把所有工具名挤在一页。

**讲述提示：**演示一条“检索 → 编辑 → 查看差异 → 运行测试”的短流程。说明扩展工具仍受确认策略约束。

---

### 第 5 页｜亮点二：后台任务有进度、有记录

**本页要传达：**耗时任务可以后台执行，用户不必一直守在当前对话里。

**建议上屏内容：**

- `/dispatch` 可分析任务适合同步处理还是异步处理；用户也可直接创建后台 Job。
- Job 持久化保存状态与事件；前端通过 SSE 展示实时进度。
- 用户可查看任务列表、进入详情、取消任务；指定来源会话时，完成结果写回会话。
- 执行面板同时呈现待办、本轮工具和后台任务，让“正在做什么”可见。

**画面建议：**按时间顺序展示四帧：发起任务、任务列表、进度事件、最终结果。可用同一个真实任务录屏截取关键画面。

**讲述提示：**强调“任务记录持久化”和“进度可查”。不要把任务记录持久化表述为进程意外退出后必然自动续跑。

---

### 第 6 页｜长任务管理：项目、检查点与定时调度

**本页要传达：**Venus 为跨天任务提供明确的状态载体，让下一次对话有上下文可接。

**建议上屏内容：**

- **项目：**记录目标、里程碑与当前活跃项目；会话可查询或切换项目。
- **检查点：**保存当前进度、下一步和阻塞信息，方便后续恢复工作。
- **待办：**把任务拆成可更新状态的条目，前端同步展示。
- **定时任务：**到点后创建异步 Job，可用于固定频率的信息整理或例行检查。

**画面建议：**一条项目时间线：目标 → 里程碑 → 检查点 → 下一次执行。时间线下方展示一条定时任务如何进入后台任务台。

**讲述提示：**用一个具体任务解释，例如“每周检查仓库测试并汇总问题”。不要声称所有复杂任务都能在没有人工介入的情况下自动完成。

---

### 第 7 页｜亮点三：记忆有层次，也能纠正与遗忘

**本页要传达：**跨会话记忆记录用户明确表达的信息，同时保留来源和修正入口。

**建议上屏内容：**

| 层次 | 保存什么 | 展示重点 |
| --- | --- | --- |
| L0 原文归档 | 任务消息原文 | 提供追溯来源 |
| L1 原子记忆 | 明确的偏好、约束和决定 | 可纠正、可删除 |
| L2 场景归纳 | 与同一目标有关的任务经验 | 需要时再读取正文 |
| L3 长期画像 | 稳定偏好 | 给后续会话提供简短背景 |

**可补充的两个能力：**动态 Skill 将重复成功的流程形成候选；CodeGraph 为代码符号和调用关系提供检索与影响分析。

**画面建议：**左侧为四层记忆结构，右侧放一个简短示例：“用户明确提出的测试偏好 → 保存来源 → 下次任务引用 → 用户纠正”。

**讲述提示：**记忆提取采用保守规则，用户可以检查和修改。不要使用“系统自动学会用户一切习惯”这样的表述。

---

### 第 8 页｜工程亮点：控制上下文与工具开销

**本页要传达：**工具和历史变多后，Venus 通过分层处理保持任务所需信息可用。

**建议上屏内容：**

1. **工具选择：**规则与本地路由模型按任务筛选工具，核心工具始终可见；路由失败回退完整工具集。
2. **按需加载：**启动时注入 Skill 清单，需要时再读取全文。
3. **历史处理：**分层预算、结构化压缩和旧消息检索配合使用，关键约束缺失时拒绝替换摘要。
4. **结果处理：**长工具输出保留开头、错误和结尾；完整结果可通过引用取回。
5. **观测：**用量接口记录调用、缓存和压缩信息，便于验证实际效果。

**画面建议：**展示“任务请求 → 工具筛选 → 主模型执行 → 结果压缩与取回”的流程。数字节省率只有在现场实测或评测记录可核验时再放上屏。

**讲述提示：**把这一页讲成工程取舍：减少无关内容进入上下文，同时保留失败信息和取回原文的路径。

---

### 第 9 页｜亮点四：敏感操作有清晰的控制点

**本页要传达：**Agent 能操作电脑，因此确认、隔离和回退是核心功能。

**建议上屏内容：**

- **五种确认模式：**自动、严格、信任、只读、计划；不同场景可切换执行权限。
- **变更可检查：**精确替换前展示 diff；文件修改有备份，可用 `undo` 回退。
- **执行有边界：**危险命令拦截，沙箱可限制工作区和网络访问；超时确认按拒绝处理。
- **紧急止停：**提供快捷键和屏幕角落止停机制。

**画面建议：**用一条“读取 → 提议修改 → 人工确认 → 执行 → 审计/回退”的流程，突出人在哪一步能介入。可配一张真实确认弹窗截图。

**讲述提示：**说明信任模式是用户主动选择的高权限模式，不应把它和默认行为混淆；默认自动模式仍会询问敏感写操作。

---

### 第 10 页｜团队协作：先建立身份与共享边界

**本页要传达：**团队功能以独立 Hub 为中心，成员和设备都有明确身份，个人环境仍保持私有。此页标注“当前开发版”。

**建议上屏内容：**

- 一个 Hub 对应一个团队；远程连接通过 Tailscale Serve 的 HTTPS 地址进入，仅让后端监听本机 loopback。
- 管理员发放一次性邀请，成员提交申请，管理员核验并批准；每台设备领取独立凭证，可单独撤销。
- 团队 Job 按 owner、visibility、project_id 控制列表、详情、进度、取消和确认待办的可见范围。
- 团队 Hub 使用隔离模式；个人会话、个人记忆、成员本机屏幕和键鼠不进入共享项目。

**画面建议：**画出“成员 A / 成员 B → Tailscale Serve → 团队 Hub”的连接关系，个人本机资源用浅色边框留在各成员一侧。

**讲述提示：**重点解释“身份、设备、项目范围”是三个不同层次。不要称为已经完成的公网多租户服务。

---

### 第 11 页｜团队项目：代码变更经过隔离与审阅

**本页要传达：**团队 Agent 产生的代码改动先进入独立工作区，再以明确文件范围提交审阅。此页同样标注“当前开发版”。

**建议上屏内容：**

1. 初始化团队项目时明确列出共享路径，只把这些文件放入 Hub 的项目仓库。
2. 每个团队任务获得独立分支和 worktree，避免任务直接改共享主线。
3. 发起人选择明确的文件路径提交变更单；成员查看目的、diff 和提交 SHA。
4. 审阅绑定提交 SHA；基线变化需要显式刷新，新的提交会使旧批准失效。
5. 合并检查目标 HEAD；已合并改动需要回退时，以新的变更单再次审阅。

**画面建议：**用 Git 分支图串起“共享主线 → 任务 worktree → 变更单 → 审阅 → 合并”。图旁放一张实际 diff 界面的局部截图。

**讲述提示：**这一页的关键词是“明确共享范围”和“审阅具体版本”。不要把尚未实现的团队任务插话或通用资产发布列为当前能力。

### 第 12 页｜可展示的产品体验与工程证据

**本页要传达：**项目既有用户可见的交互，也有支撑持续开发的验证体系。

**建议上屏内容：**

- **桌面体验：**VenusChat 已接入会话列表、流式对话、工具卡片、确认弹窗与执行面板。
- **多入口共用后端：**CLI、网页和 Telegram 可以按场景使用相同的任务与会话能力。
- **自动验证：**仓库包含工具调用、会话、任务、记忆、安全、团队协作等测试；CI 在 Windows 和 Ubuntu 上检查主 Agent。
- **演示路线：**输入一个小型仓库任务 → 观察工具与任务进度 → 查看确认和差异 → 展示结果及后续会话中的记录。

**画面建议：**左半页用一张干净的 VenusChat 真实截图；右半页用 3～4 张小幅证据图串起演示流程。CI 截图应显示真实运行日期和结果，不要拼接不存在的通过记录。

**讲述提示：**本页可以转入现场演示。演示任务预先固定在可恢复的测试工作区，避免现场修改个人文件。

### 第 13 页｜总结与下一步

**本页要传达：**Venus 已形成可执行、可追踪、可控制的 Agent 工作流；后续改进有清晰边界。

**建议上屏内容：**

- **当前已具备：**多入口执行、异步任务、跨会话记忆、安全控制，以及当前开发版的团队身份与项目审阅流程。
- **近期重点：**完善团队任务进行中的协作交互；补齐通用团队资产发布；继续打磨 Hub 部署与故障恢复体验。
- **结束语：**让用户能看见 Agent 正在做什么、决定关键操作是否继续，并在下一次任务中复用已经确认的信息。

**画面建议：**用一句结束语配三张真实画面局部：任务进度、变更确认、团队审阅。避免在结尾堆功能清单。

**讲述提示：**团队任务插话、通用资产发布仍是后续事项；不要写成现有功能。若是对外发布汇报，先对当前工作区的未提交变更做一次版本确认。

## 现场演示建议

为控制时间，现场只演示一条主路径，其余功能用截图说明。

1. 预先准备一个无敏感数据的小型测试仓库，确保任务可以在几分钟内完成。
2. 在 VenusChat 输入明确任务，例如“运行指定测试，定位一个失败，并给出最小修复方案”。
3. 展示任务进入后台、进度更新和工具卡片；如涉及修改，展示 diff 与确认环节。
4. 展示任务结果、文件差异和会话记录。需要演示记忆时，使用预先创建且可核验来源的偏好。
5. 团队流程建议用预录的双设备操作片段或截图，避免现场组网状态影响主线。
